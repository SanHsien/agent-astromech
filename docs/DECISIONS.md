# 維護決策

## 2026-08-24：採用維護型 fork

專案命名為 agent-astromech，保留MIT 歷史、原作者歸屬與 10-skill 介面，只新增維護治理與跨平台開發環境。原因是上游已有真實產品、發布與回歸矩陣；重新包裝核心只會增加漂移。

## 2026-08-24：Windows-first 不等於假裝 NTFS 是 POSIX

Windows 使用 PowerShell 作 canonical entrypoint，產品 shell 測試由 Git for Windows Bash 執行。NTFS 無法用 `ls -l` 證明 `0600`，因此 Windows 只允許該單一斷言明確 skip；Linux CI 仍須完整通過，沒有平台豁免。

## 2026-08-24：不建立 Python 套件

Python 維護工具只使用標準庫與 `gh`，不新增 `pyproject.toml` 或 requirements；`package-lock.json` 僅固定 `skills`／`skills-ref` 維護工具及其 integrity。repo 的交付物是 Agent Skills，不是 Python library。

## 2026-09-11：免安裝簡版補齊到判準涵蓋的每一支；`blind-review` 依判準不做

起因很特別：D-06 測試時被**誤按門鈴**的那個 session 真的開工了，交出兩份 agent-astromech 盤點報告
（adapters 是否過期、prompts 與 skills 是否同步）。誤喚醒的成本因此有了具體形狀——
一個正在做別的事的 session 被拉去做了兩份報告。但報告本身品質很好，裡面的發現照樣採納：

- **`recap`、`token-optimizer` 補上簡版（中英各一）。** 判準是 `CLAUDE.md` 連動表寫的「規則類 skill 適用」，
  而 README 相容性矩陣自己就把這兩支標成「規則類」——自己訂的判準、自己標的分類，卻沒有簡版，是缺漏。
- **`blind-review` 不做簡版。** 它的矩陣格**沒有**標「規則類」（寫的是「需子代理」與「另開空白對話當攻擊者」），
  判準不命中。它的核心是「攻擊者拿不到對話」這個**操作安排**，不是一段可以貼進常駐欄的規則——
  貼進常駐欄的東西，恰好就在對話裡。重查條件：若矩陣把它改標為規則類，再補。
- adapters 的 Codex 版號（0.145／2026-07）補上 0.150.0 的再驗與執行層結果；
  README 目錄樹補一句「其餘工具由 `npx skills` 直接安裝，不需移植包」，回答「為什麼只有 openai 一個 adapter」。

📌 報告原檔保留在維護者本機 `workspace/notes/handoffs/`（不進 repo），並註記處理結果。

## 2026-09-07：修掉一個錯誤行為後要再測一次，錯誤常常只是換一件合規的外衣

D-06（誤喚醒防呆）實測跑了三輪，中間那輪是關鍵。

第 1 輪：目標專案有 4 個新鮮 session，agent 自己挑了「最新啟動的那個」按下門鈴，
事後才補「如果不是你要的跟我說」。規格明寫「超過一個 → 問使用者」，這是失敗。
於是加上「🔴 不准自己挑」。

第 2 輪：它**確實沒有自選了**——改成從上一輪那張舊卡的 `rung-at` 欄位反推出路由，
然後「沿用既有路由」。而沿用 `routing.md` 是規格**允許**的行為。
也就是說：第 1 輪的亂挑，變成了第 2 輪的合法依據。**壞路由會自我延續，
而且每一次沿用看起來都完全合規。**

第 3 輪（再補「路由要有出處：只有 `decided-by: user` 能免問沿用」）才通過。

定為慣例：
- **修完行為規則要用同一條路徑重測**，而且要在**乾淨環境**——上一輪的產物會變成下一輪的輸入。
- **凡是「記住使用者的決定」的機制，都要記錄決定的出處**。沒有出處的偏好無法分辨
  「使用者要的」與「上次自己猜的」，於是猜測會取得跟決定一樣的地位。
- 一般化：**修掉症狀後要問「同樣的錯誤還有沒有別條合規的路徑可以走」**。

## 2026-09-07：三項「未驗」結案——不是做完，是決定不做，並寫明理由

盤點剩餘未驗項時，把三項從「待辦」改判為「結案」，理由各不相同：

| 項目 | 判決 | 理由 |
|---|---|---|
| 免費方案帳號實測 | **刻意不驗** | 需另外申請帳號，維護者明確不為此申請；借他人帳號不具代表性。README／SKILL.md 已寫「未實測」，**那句話本身就是最終答案**，不需被當待辦追蹤 |
| 預設關搜尋的 codex build | **造不出，停止追查** | 已實際嘗試：`-c tools.web_search=false` 在 0.150.0 上無效（key 被認得但兩個方向都不生效）。旗標保留（無害、未來可能必要），文件據實描述，不再追 |
| `winpath` 等四項修復回貢上游 | **不回貢** | 維護者拍板。修正留在 fork；`docs/UPSTREAM.md` 的衝突面清單就是為此存在，下次 fetch 以 fork 版為準 |

📌 定為慣例：**「未驗」有三種，要分清楚**——①還沒排到（真待辦）②被外部條件擋住
（要寫解除條件）③**決定不做**（要寫理由，然後停止追蹤）。
把第③種留在待辦清單裡，會讓清單永遠清不完，也讓真正的待辦被稀釋。

## 2026-09-06：要證明「機制有沒有發生」，就看機制的直接證據，不要用產出內容回推

`ai-search` 的 `-c tools.web_search=true` 是否為搜尋成因，前後查了兩輪，**第二輪推翻第一輪的證據**。

第一輪：拿掉旗標它照樣答出當前版號，於是判定「旗標非成因」。**這個推論站不住**——
答得出來不等於查過，那個版號可能本來就在模型知識內，中間隔著一個沒被排除的解釋。
差一點就以錯誤理由寫進 release note。

第二輪：改用 `codex exec --json` 直接數 `web_search` 工具事件，並換一個本機絕對答不出的問題。
（先前用「現在 UTC 幾點」是壞題目——它跑本機 PowerShell 就答完了，事件流裡零個 `web_search`，
差點被讀成「旗標無效」。）結果：`true` 與 `false` 兩組**都有** `web_search` 事件，關不掉；
`--strict-config` 不報錯代表 key 被認得但無效。結論與第一輪相同，但這次站得住。

定為慣例：**驗「有沒有發生」用直接證據（工具呼叫事件、log、退出碼），不用產出內容回推。**
同源的第二條：**計數型驗證要先確認退出碼**——本輪另一處用 `wc -l` 數 `--date yesterday` 的輸出
得到「7 筆」，那 7 其實是 traceback 的行數。失敗會偽裝成一個看起來合理的數字。

## 2026-09-06：憑證由使用者自己設進環境，代理人不接收明文金鑰

補 gemini 執行層時需要 `GEMINI_API_KEY`。處理方式定為慣例：
🚫 **不請使用者把金鑰貼進對話**——貼進去就進了對話記錄，事後無法收回。
✅ 使用者自己 `setx` 設進環境，代理人從登錄檔讀進**子行程環境變數**、全程不列印其值，用完清除。
✅ 用前先**驗形狀不驗內容**（長度、是否等於文件裡的佔位字、是否符合該廠商的格式），
   確認拿到的是真金鑰而不是被原樣複製的範例字串——本次就先擋掉了這個可能。
✅ 帳號登入（OAuth／瀏覽器流程）一律請使用者自己做，代理人不代登。
測試一律在隔離 `HOME` 進行，事後確認真實設定目錄未被動到。

## 2026-09-06：外部阻礙會過去，「未驗」不是可以長住的狀態

v0.8.2 收尾時留了兩項「未驗」，理由都成立：codex 額度用盡、本機沒裝 Gemini CLI。
但「理由成立」跟「可以放著」是兩件事。隔天額度恢復，兩項連同一項自 repo 建立以來
從沒跑過的 CROSS-05，全部補完。

由此定為慣例：**帶外部阻礙的「未驗」要寫上解除條件與重跑方式，並在條件解除時主動回頭跑**，
不是列進誠實帳就算處理完。誠實帳是為了不謊報，不是待辦事項的垃圾桶。

補完這一輪還意外推翻了一個宣稱：`ai-search` 送給 codex 的 `-c tools.web_search=true`，
上游文件寫成「這是 ai-search 與 ai-review 的關鍵差異」。做了上游沒做的負對照
（拿掉旗標、其餘相同）後發現**照樣會搜**，本機 config 也查無相關設定。
旗標保留（無害、在別的 codex build 上可能仍必要），但因果宣稱已據實改寫。
📌 一般化：**單次陽性推不出因果**。「加了 X 就有 Y」要能成立，得有人真的把 X 拿掉試一次。
⚠️ **後續更正（同日稍晚）**：上面這個負對照的**結論對、理由錯**。「拿掉旗標照樣答得出來」
不足以證明它搜過（答案可能來自模型知識）。真正的證據是第二輪數到的 `web_search` 工具事件——
見本檔「要證明機制有沒有發生，就看機制的直接證據」那則。

## 2026-09-06：實測記錄的日期以獨立來源為準，不是以本機時鐘為準

v0.8.0／v0.8.1 兩個 commit 的 author 時間戳是 **2026-09-02**，但那批工作實際發生在 **2026-09-05**——
當時本機時鐘慢了約三天，事後才同步回來。發現方式很偶然：跑 F-02 的即時查證時，
後端回的答案裡帶著「Codex 0.153.4 於 2026-09-04 發布、是昨天的事」，與本機 `date` 對不起來。

規則：**帶日期的實測記錄，日期要能對得上一個獨立來源**（網路查證的回答、release 的 `published_at`、
CI run 的時間戳），不能只抄本機 `date`。已推送的 commit 時間戳不回頭改寫（不 force-push），
本檔與 `docs/TEST_PLAN.md`、`docs/UPSTREAM.md` 內的日期一律以實際日期為準，
因此會與 git log 差三天——**這個落差是刻意保留的記錄，不是筆誤**。

📌 這件事本身是 repo 主題句的另一個面向：`save-all`／`new-mission` 都寫著「落地紀錄的時間
別憑印象寫、要從機器取」。這次的教訓是再往下一層——**機器也會錯**。

## 2026-09-05：採納的上游程式碼要在 Windows 上「真的跑一次」，不是只跑矩陣

v0.8.0 交付時，`ai-search` 的相容性評級與真實後端行為都掛著「沿用上游、本 fork 未驗」。
把那幾格逐一實跑之後，浮出三個**只有真跑才會出現**的缺陷：`codex.exe` 讀不懂 POSIX 路徑
（`ai-review` 也有，等於兩支腳本在 Windows 上從沒碰到過真實後端）、矩陣的 frontmatter 驗證
在 Windows 上假紅兩次（路徑＋locale 解碼）、取時區的退路在 Git Bash 印出空標籤。

結論定為慣例：**採納上游腳本時，「矩陣全綠」不等於「在本平台可用」**。矩陣的 stub 是 sh 腳本，
天然吃得下 POSIX 路徑，看不見原生 exe 的介面差異。凡是會呼叫外部程式的 skill，採納時
至少對真實後端跑一次，並把該次觀察寫進 `docs/TEST_PLAN.md`——即使結果是失敗（本次就只驗到
`failed_quota`，因為帳號額度用盡）。**驗到失敗分類正確，也是證據；宣稱未驗，不是。**

## 2026-08-24：upstream 水位分離

commit、PR、issue 與 branch head 分別記錄。Baseline 表示已審查，不表示已合併；每次只處理水位之後的新狀態，避免重複成本與標題式判斷。
