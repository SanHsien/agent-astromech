# /blind-review — 對抗式審查與導讀

要人看一份 AI 寫的改動之前，先做兩件事：
**找一雙沒有前情的眼睛去攻擊它**，再**把當初的取捨寫下來**，
最後交出去的不是裁決，是一份**導讀**——告訴人該把注意力放在哪。

> 🤖 Astromech 時刻：R2 插進 Death Star 的接口時，沒讀過任何作戰簡報。
> 也正因為沒有前情，它讀回來的是儀表上真的亮著的那盞燈，不是你以為應該亮的那盞。

## 為什麼需要

- **自審的上限是脈絡，不只是模型。** 寫東西的那個代理，是沿著一串假設一路推過來的；
  叫它「再檢查一次」，它會沿著同一串假設再走一遍，然後確認自己本來就相信的事。
  這裡換掉的是**脈絡**——攻擊者拿不到對話，所以繼承不到那串假設。
  （想換的是**模型家族**，那是 [`ai-review`](../ai-review/SKILL.md) 的工作。兩者可以疊。）
- **人要看 diff 之前，缺的不是裁決是導讀。** 「通過／不通過」告訴你結果，
  不會告訴你該盯哪三行。冷讀一份幾百行的 diff，人會平均分配注意力——
  而風險從來不是平均分布的。
- **當初為什麼這樣選，只有主代理知道。** 那些取捨活在對話裡，對話一關就蒸發，
  然後半年後沒人答得出「這裡為什麼不用另一種寫法」。導讀是把它落檔的最後機會。

## 步驟

### 0. 界定範圍並凍結

先講清楚審的是什麼：某個 PR、某條分支對主線的差異，還是工作區當下的未提交改動。
**記下當下的版本識別碼（提交雜湊，或 diff 的雜湊）並寫進最後的導讀。**

⚠️ 這步是防 TOCTOU 的：送審之後又改了東西，審的就是舊版，而導讀不會自己知道。
沒有識別碼，事後誰也證明不了那份導讀對應的是哪一版。

### 1. 派攻擊者（子代理，旗艦檔）

給它**只有兩樣東西**：改動本身，加上一句原始需求。
🚫 **不要把對話摘要餵進去**——那正是要隔離的東西。餵了就退化成自審。

工具給唯讀就好（讀檔／搜尋／跑測試），**不給寫入**。攻擊者的產出是意見，不是提交。

攻擊沿兩軸，各自有硬性收件標準：

- **正確性** —— 只收「**具體輸入 → 錯誤輸出**」形式的失敗劇本。
  🚫 「這裡可能有問題」「建議加強錯誤處理」一律退回：講不出怎麼觸發，就不是發現。
  優先攻邊界值、空集合、併發、失敗路徑、以及「安靜失敗」（回報成功但實際沒做到）。
- **簡潔性** —— 重複的邏輯、可以整段刪掉的東西、為了想像中的未來寫的抽象層、
  以及**早就存在卻沒複用的既有機制**。這一軸的價值在於：寫的人正忙著讓它跑起來，
  沒有餘裕問「這段是不是根本不必存在」。

### 2. 主代理補「假設與設計決策」

這段**只有主代理寫得出來**，因為只有它經歷過那些取捨。逐條寫，每條四行：

```
決策：<做了什麼選擇>
當時的選項：<還有哪些做法>
選這個的理由：<為什麼>
什麼情況下這個選擇會錯：<失效條件>
```

最後一行是重點，也是最容易被跳過的一行。寫不出失效條件，通常代表那不是個決策，
是個沒意識到自己在選的預設值——那本身就值得寫進導讀。

### 3. 產出導讀（三段，就這三段）

1. **先看哪裡** —— 最多三處，每處給位置（檔案與行）＋一句「為什麼是這裡」。
   超過三處等於沒有重點。排序依據是「錯了傷害最大」，不是「改動行數最多」。
2. **假設與設計決策** —— 步驟 2 的產出，原樣放進來。
3. **我沒驗證的部分** —— 誠實列。跑過哪些測試、哪些路徑一次都沒跑到、
   哪些結論是推論不是實測。沒有就寫「無」。

導讀開頭標上步驟 0 的版本識別碼。

### 4. 裁決，然後停手

用三選一收尾：`ship`／`fix-first`／`rethink`，附一句理由。

🚫 **不要順手把發現的東西改掉。** 攻擊者的意見有真有假（它沒有脈絡，這是優點也是限制），
主代理**要在導讀裡回應誤報而不是刪掉它**——「它提了 X，這裡不適用，因為⋯⋯」
本身就是有用的資訊。改不改、改哪些，是人的決定。

## 攻擊者 prompt 骨架

```
你沒有看過任何相關對話，這是刻意的。你只會拿到改動本身與一句原始需求。

原始需求：<一句話>
改動：<diff 或檔案清單>

沿兩軸攻擊，各自獨立成段：

A. 正確性
   只提得出「具體輸入 → 錯誤輸出」的問題才寫。講不出觸發方式就不要寫。
   每條格式：位置 / 觸發輸入 / 預期 / 實際 / 為什麼。

B. 簡潔性
   重複、可整段刪除、過度抽象、該複用既有機制卻另寫一份。
   每條要指出「刪掉或換掉之後長什麼樣」。

規則：
- 只審不改，不要動任何檔案。
- 兩軸都沒有發現就寫「無」。禁止湊數——湊出來的第三條會稀釋前兩條。
- 你缺脈絡，這是設計。有不懂的地方直接寫成問題列在最後，不要自己腦補理由。
```

最後那條很重要：攻擊者的「這裡為什麼不用 X？」不是雜訊，那正是主代理該在
導讀裡回答的問題——也是讀導讀的人最可能問的同一個問題。

## 🚦 鐵律

- 🔒 **攻擊者不吃對話** —— 餵了對話摘要就退化成自審，整支 skill 失去意義。
- 🚫 **只審不改** —— 攻擊者唯讀；主代理在 blind-review 期間也不動手修。
- ✅ **失敗劇本才算發現** —— 「可能有問題」不收；「無」是合法且值得信任的答案。
- 📝 **導讀要標版本識別碼** —— 沒有它，事後證明不了審的是哪一版（TOCTOU）。
- ⚠️ **誤報要回應不要刪** —— 攻擊者問錯的地方，往往是讀者也會問的地方。
- 🔁 **最多三處重點** —— 超過三處就不是導讀，是第二份 diff。

## 進階

**疊上跨模型二審**：本 skill 換脈絡，[`ai-review`](../ai-review/SKILL.md) 換模型家族，
兩者攔的是不同東西。要都做的話順序是：先 blind-review（拿到攻擊結果與導讀草稿），
再把**導讀草稿**送 ai-review，最後才定稿。反過來做，二審看到的是還沒被攻擊過的版本。

**接上收尾自檢**：[`damage-report`](../damage-report/SKILL.md) 的五問是對照原始需求跑的，
與這裡的兩軸互補——五問問「做對了嗎」，這裡問「哪裡會壞、為什麼這樣寫」。

**把導讀變成可分享的頁面**：環境若能產出可分享的網頁或文件，就把導讀發成一份，
連結交出去。導讀的價值在於**人在別的地方、別的時間也讀得到**；
只活在終端機捲軸裡的導讀，等於沒寫。
